Part A · 特性需求（继承 v1.0，不重写）

§1 背景与目标

EZR 数据同步采用「两级队列」：定时任务先把业务表中变化的记录写入待推队列（report.sync_data），再由推送任务逐条调用 EZR 接口。第一级任务是本特性的改造对象。

现网已证实：第一级任务在单次扫描窗口内待入队记录超过两批（10000 条）时开始漏扫，漏掉的部分不报错、不影响任务成功状态，属于静默丢数据。2026-08-03～08-04 的积分流水回灌即为典型事故现场。

目标：让第一级任务在任意数据量下保证「符合条件的记录 100% 入队」，且作业必定正常终止（不死循环、不超时挂死）。

衡量指标：单次扫描窗口内，待入队记录数与实际入队记录数的差额为 0。

  • CK 线 CkDataXXxlJob 7 个 preSync*Handler + TH 线 THDataXXxlJob 7 个同名 preSync*Handler（v1.0 只写了 CK 线，见 §13.1 勘误 E7）

§6 用例（UC-preSync-cursor-paging-NNN）

UC 名称 主流程 异常流
UC-001 全量入队 任务触发 → 取一批 → 过滤 → 入队 → 推进位点 → 取下一批 → 直至取尽 取数异常：抛出，由调度记录失败，位点不推进，下轮重来
UC-002 全批被过滤 取一批 → 全部被过滤 → 入队空集 → 位点仍推进 → 取下一批 无
UC-003 重跑幂等 任务二次触发 → 已入队行不满足取数条件 → 直接跳到新数据 无
UC-004 数据取尽 某批返回条数 < 批量大小 → 结束 无

关键约束（来自 UC-002）：位点推进必须基于「取数返回的原始批次」，不得基于「过滤后的批次」。这是本设计唯一的强约束，违反即死循环。

补充（v1.0 未写明）：位点是 Job 方法内的局部变量，不落库。因此「作业中途失败」与「作业从未跑过」在下一轮看来完全等价 —— 下一轮仍从 lastId = 0 重扫整个窗口，靠 version 幂等保证不重复入队。这是「失败可重入」的前提，不要把位点持久化到 sync_data 或调度参数里。

filtered 被手机号 / 激活状态过滤掉的条数 scanned − passed（有过滤的链路）
passed 通过业务过滤、提交给 syncEzrPreHandler 的条数 ⚠️ 黑名单在服务层再过滤，故 passed ≥ 实际写入 sync_data 的行数；实际写入数以 §18.3 的 SQL 为准

§16 机制说明

§16.1 现有 offset 漂移是怎么发生的

  1. 取数 SQL 无 ORDER BY，分页由 PageHelper.startPage(page, 5000, false) 施加 → OFFSET (page-1)*5000。
  2. 取数条件含 a.version > IFNULL(b.version, -1)：记录一旦入队（syncEzrPreHandler 写回 version = 业务表 version，@716），该行从结果集中消失。
  3. 第 1 页取 5000 条并入队 → 这 5000 条从结果集消失 → 第 2 页的 OFFSET 5000 在已缩短的结果集上继续跳过 5000 条 → 每翻一页实际跳过 5000 条本该入队的记录。
  4. 结果：单轮只入队约前 5000 条，其余静默丢失，且作业成功退出。

证据：7 段 <select> 全文见 SyncEzrMapper.xml:4 起（@4-161），无一条 ORDER BY；PageHelper.startPage 调用见 SyncEzrServiceImpl.java:71 等 7 处。

§16.2 游标语义与单调性前提

  • 开区间：a.id > #{lastId}，首轮 lastId = 0。
  • 单调推进：每轮 lastId = max(batch.refId)，且 batch 非空 → lastId 严格递增 → 不会出现「同一批反复取」。
  • 单调性前提：业务主键须随创建顺序递增。实际生成机制是 Redis SEQ（应用侧发号，不是 DB 自增）：<前缀数字><yyMMdd><9 位日内序号>（SEQUtil.java:74 @74-111，日前缀见 RedisSEQTimer.java:81 @81-83，DAY_FORMAT_PATTERN = "yyMMdd"；由 SEQGenerator.java:9 挂到 MyBatis-Plus IdentifierGenerator）。7 张业务表的 id 全部是这一套（无一例外是 AUTO_INCREMENT）。
    • ✅ 日内严格递增；跨日递增（日前缀变大）；id 数值序 ≈ 创建时间序 → 位点推进与时间窗口方向一致。
    • ⚠️ 跨实例分块分配：Redis 序列按 1000 一块分配，多个应用实例各自持块 → 存在极小概率「后创建的记录 id 反而更小」。
    • ⚠️ 批量取号接口 SEQUtil.UUIDs 位宽不同：批量发号用 String.format("%010d", ...)（10 位，@137），单发用 %09d（9 位，@86）→ 若某张表同时存在两种来源的 id，数值序 ≠ 时间序（17 位与 16 位混排）。另该接口内部自块尾往前发号（@136-138）→ 同批内 id 与插入顺序相反。
    • ✅ 游客会员特例已被 SQL 排除：customer.customer 里存在非 SEQ 的游客 id 20230615001（11 位，远低于 SEQ 区间），7 段 SQL 已用 and a.id != 20230615001 显式排除（SyncEzrMapper.xml @94 / @115 / @159）→ 不会破坏位点单调性。
    • 影响：上述两类例外记录本轮漏扫，但因窗口按 update_time 滚动、且位点不落库，下一轮会补上（不丢数据，只是延后一轮）。核验 SQL 见 §18.4。

§16.3 位点必须取「原始批次」

若把位点写成「过滤后集合的最大 refId」：

原始批 = [A(被过滤), B(被过滤)]      → 过滤后为空集
lastId = max(空集) = 上一轮 lastId   → 下一轮取回同样的 A、B → 死循环

因此位点计算必须写在 filterValidRefIds 之前，且作用于 batch（原始批）。这是本设计唯一的强约束。

§16.4 幂等：为什么重跑不会产生重复行

三层保障：

层 机制 位置
取数层 a.version > IFNULL(b.version, -1)：已入队且业务表 version 未变的记录不再出现在结果集 7 段 <select>（SyncEzrMapper.xml @14 / 33 / 53 / 74 / 95 / 133 / 152）
落库层 syncEzrPreHandler 按 DTO 的 id（= b.id）决定 insert 还是 update：id 为空 → insert，非空 → updateBatchById SyncEzrServiceImpl.java:717 @717-722
调度层 位点是局部变量，失败后下轮从 0 重扫；重扫到的已入队记录被取数层排除 §14.5 模板

列 写入值 含义

  • AC-06（重跑不产生重复）成立：重跑时同一业务记录的 b.id 已存在 → 走 update 分支 → 不新增行；
  • AC-10 只能核验「改造上线后新增的行」不重复，存量 9,656 组重复不计入（§18.3 ③ 已按上线时间收窄）；
  • scanned 计数含扇出行 → 不等于去重后的业务记录数，对账时按 §18.3 ① 的口径（同一条 SQL，同样会扇出）比较才成立。

§16.5 终止性

  • 循环条件 batch.size() >= pageSize：只有「满批」才继续。
  • 每轮 lastId 严格增大且上界为表内最大 id → 轮次有限。
  • 轮次上界：设窗口内待处理 N 条、批量 P=5000 → 轮次 ≤ ⌈N/P⌉ + 1（最后一次取空批用于确认取尽）。
    • v1.0 写「+2」，本详设收紧为「+1」；验收按「≤ ⌈N/P⌉ + 2」判定亦可通过（AC-09 留有余量）。
  • 全批被过滤时：batch.size() == 5000 → 继续；位点已推进 → 下一批取的是更靠后的记录 → 不会死循环（§16.3）。

§16.6 与窗口、推送侧的关系

  • 窗口不滑动：parseJobParam 在循环外一次算好 [startDate, endDate]（@245-261），窗口 = [now − B 分钟, now − A 分钟]，A/B 来自 XXL 调度参数。扫描期间的新变更 update_time 超出窗口 → 本轮不取 → 下一轮窗口覆盖到时入队。
  • 推送侧不受影响：推送侧 getRefIds 用 ge("id", startId) + orderByAsc("id")（@771-780），已是游标式，且 page 恒为 1。
    • ⚠️ 两处推送侧既有的怪癖（不在本特性范围，仅记录以免误判为本次引入）：① ge 是 >= 不是 > → 上一批最后一行每轮会被再读一次（靠状态位已变更才不重复推）；② skipBlacklistedPending（@800-812）会把黑名单行从本批结果里剔除，导致返回条数小于 pageSize，推送循环的退出条件 size >= pageSize 可能提前结束，且 startId 取自过滤后列表的最后一行。两者均与本次改造无关。
  • 两侧衔接：靠 sync_data.version —— 入队写业务表 version，推送侧读 sync_status_1 ∈ (0,2) 的记录。

§17 可观测性

每批日志（XxlJobHelper.log，格式串用 {} 占位）：

preSync progress lastId=1260518120000001, batch=5000, scanned=12000, filtered=37, passed=11963

结束日志：

preSyncEzrCustomerAccountTransactionChangeHandler end lastId=1260518130000002, scanned=25000, filtered=412, passed=24588 <----

口径：

字段 含义 用途
lastId 本轮处理到的最大业务主键 判断「扫到哪儿了」「是否跑完」
batch 本批原始条数 判断是否满批（满批 = 后面还有）
scanned 累计原始条数 与「窗口内候选数」对账（§18.3）

passed 累计提交入队条数 与 sync_data 实际新增行对账

passed 不等于 sync_data 实际新增行数（黑名单在服务层过滤）。以 §18.3 的 SQL 为准。
